### US-035: The window starts at the first post, on the server clock
**As an** operator, **I want** the measurement window anchored to the first posted publication and stamped by the server **so that** a video that sat in review for days still gets its full window (today `approved_at` comes from the browser unvalidated and posting can happen days later).
**Points:** 2
**Status:** Done
**Acceptance criteria:**
- [x] Given approve, when it stamps the window anchor, then the timestamp is generated on the server (an unparseable client `now` is refused — folded into the Wave 2 landing: verify before starting) — the anchor stamp is written by the server at the first post (`_stamp_first_post` in api/app.py uses `_now()`, called from the two routes that reach `posted`: the publications route on both its fresh and duplicate-url paths, and the manual URL route), pinned by `test_the_first_post_stamps_the_window_anchor_on_the_server_clock` and `test_pasting_the_manual_url_stamps_the_first_post_too` (tests/test_api.py); `approved_at` stays what the browser sent (it is displayed), and the unparseable-`now` refusal was verified already landed: `test_approve_with_an_unparseable_now_is_refused` (tests/test_api.py).
- [x] Given the first publication that reaches `posted`, when the window anchor does not exist yet, then the window starts there; the complete guard uses that anchor — the experiments table gains `first_posted_at` (legacy-safe `_ensure_first_posted_at` startup migration in store/db.py, pinned by `test_legacy_rows_upgrade_without_the_first_post_stamp`, tests/test_store.py); the guard and `_clicks_window` share ONE anchor, `_window_anchor` = the later of the approval and the first post (a lying browser clock can only lengthen the window; an experiment never posted falls back to approval alone), so a month-old approval with a fresh post is back inside its window: `test_the_first_post_stamps_the_window_anchor_on_the_server_clock` asserts the 409 names an end anchored at the post, and `test_clicks_after_the_post_are_windowed_and_pre_post_clicks_are_not` pins the counter on the same anchor; the stamp is written once — `test_a_second_platforms_post_never_moves_the_first_post_stamp`.
- [x] Given Board and Post, when an experiment is approved, then the window end date is shown before the operator can hit the 409 — `_experiment_json` serves `first_posted_at` and a server-derived `window_end`; the Board's Selected facts show both rows and the Post panel shows `measurement window ends …` beside the Complete button (web/src/App.jsx), verified in a real browser against the temp lab: Board facts `window ends 2026-11-26T21:39:12Z` and the same line on Post above `Complete experiment`; `npm run build` passes.
- [x] Given an experiment never posted, when complete is attempted, then the guard falls back to the approval timestamp rather than allowing immediate close — `_window_anchor` with no post stamp is `approved_at` alone, pinned by the pre-existing `test_complete_inside_the_window_is_409_naming_the_end_unless_forced` (recent approval, never posted → 409) and `test_complete_after_the_window_or_without_approved_at_needs_no_body` (window closed → 200), both tests/test_api.py; the live-migrated legacy row in the browser run showed the same fallback (`first_posted_at —`, window end = approval + 7 days).

Note on a deliberate test change: `test_flow_from_starter_grid_to_a_draft_proposal` (tests/test_flow.py) asserted an unforced complete always succeeds after approving eight days ago. That guarantee is exactly what this story removes — the flow now posts first, which stamps the anchor at run time, so the test pins the new behavior (unforced complete → 409 naming the window end, then the override closes it), which strengthens the flow by covering the 409 and the override end to end.
