### US-025: Clicks are a log the measurement window can read
**As an** operator, **I want** every click stored with its time **so that** the day-7 verdict uses only clicks inside the window and history is never flattened into one counter.
**Points:** 3
**Status:** Done
**Acceptance criteria:**
- [x] Given a click on /r/{code}, when it is recorded, then a click row exists with the code, the experiment id, and a timestamp (today only a counter increments) — `add_click` appends to the `clicks` log in the same transaction as the counter (store/db.py)
- [x] Given GET /results, when clicks are reported for an experiment, then clicks inside its measurement window are distinguished from the total (a click on day 8 with a 7-day window is excluded from the windowed count) — `clicks_window` on every results row; `test_results_separate_windowed_clicks_from_the_total` (tests/test_api.py) excludes post-window clicks and windows nothing before approve
- [x] Given the legacy clicks counter column, when new clicks arrive, then it stays in sync with the log (counter equals total log rows for the experiment) — one transaction in `add_click` (store/db.py); the windowed-clicks test asserts both the counter and the windowed count; a legacy database whose clicks predate the log is backfilled at startup (idempotent, stamped at migration time) so the invariant holds there too — `test_legacy_click_counters_are_backfilled_into_the_log` (tests/test_store.py). Caveat: the backfill stamps unknown-time clicks at migration time, so `clicks_window` for a legacy experiment whose window is still open counts them all — the honest range given the data.
