### US-038: Snapshots honest about gaps
**As an** operator, **I want** blank snapshot fields stored as absent, not as zero **so that** "not measured" never masquerades as "measured zero" in the trend (today the dashboard sends 0 for every field left blank, and percent viewed shows 0%).
**Points:** 2
**Status:** Done
**Acceptance criteria:**
- [x] Given the Record snapshot form, when a field is left blank, then the stored snapshot keeps it absent (null), and a blank on the wire is not coerced to 0 — the dashboard sends null for every blank count, views included (the views-required guard is gone; an explicit 0 still sends 0), web/src/App.jsx `saveSnapshot`; the wire accepts null (`SnapshotIn` counts are `int | None` in api/app.py) and the writer keeps it (`record_snapshot` in metrics/pull.py passes None through instead of `or 0`); the `snapshots` columns became nullable (new schema; legacy tables rebuilt once by `_ensure_nullable_snapshot_counts` in store/db.py — SQLite cannot drop NOT NULL with ALTER — with recorded zeros keeping their meaning), pinned by `test_a_blank_count_is_stored_absent_not_zero` (tests/test_snapshots_api.py), `test_add_snapshot_keeps_absent_counts_absent` and `test_legacy_snapshots_upgrade_to_nullable_counts` (tests/test_store.py).
- [x] Given SnapshotHistory, when a field is absent, then the cell reads "—" rather than 0 — the history payload carries null and the existing `show()` already renders blank values as "—" (web/src/App.jsx); verified in a real browser: a snapshot recorded with only views filled read back `30, —, —, —, —, —` while the pre-change row kept its measured zeros (`12, 0, 0%, 2, 0, 0`); `npm run build` passes.
- [x] Given percent viewed, when views or watch time is absent, then the cell reads "—" rather than 0% — `percentViewed(views, watchTimeSeconds, lengthSec)` returns "—" when either input is blank (web/src/App.jsx), browser-verified on the same row (views present, watch absent → "—"); the results total also skips a latest snapshot whose views are absent (`_views_for`, api/app.py), pinned by `test_results_do_not_count_views_the_latest_snapshot_left_absent` (tests/test_snapshots_api.py).
- [x] Given a backdated `captured_at`, when snapshots are read back, then the order follows captured_at (folded into the Wave 2 landing: verify before starting) — already Done by Wave 2: the route normalises a parseable `captured_at` to UTC Z-form and refuses an unparseable one, and history follows captured_at; pinned by `test_a_backdated_snapshot_lands_where_its_captured_at_says` and `test_a_snapshot_with_an_unparseable_captured_at_is_refused` (tests/test_snapshots_api.py), both re-run green with this story's changes.
